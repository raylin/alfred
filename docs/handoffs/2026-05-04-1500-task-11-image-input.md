A. LINE Image Message 處理

src/index.ts:
- 偵測 message event 中 message.type === 'image'
- 從 message.id 走 LINE Content API 取得圖片:
  GET https://api-data.line.me/v2/bot/message/{messageId}/content
  Bearer auth 用 LINE_CHANNEL_ACCESS_TOKEN
  回傳 binary stream → base64 encode
- 路由到 places capability(現在 image 只有 places 處理,不走 LLM intent router)

src/integrations/line.ts:
- 加 fetchMessageContent(messageId): Promise<{ contentBase64: string, mimeType: string, sizeBytes: number }>
- 處理 binary response,轉 base64

B. Intent Router 對 Image 的處置

Image 不走 Haiku intent router(沒文字可分類)。直接 dispatch 到 places。

未來如果加新 capability 也要處理 image(例如 shopping 處理收據):在 src/capabilities/_registry.ts 的 Capability type 加 `accepts_images?: boolean`,handler 用第一個 accepts_images === true 的 capability。Phase 0+1 places 預設 true,先做註記但不需要寫多 capability dispatch 邏輯(只有一個能力,直接走它)。

寫進 ADR。

C. Image Flow

src/capabilities/places/flow-image.ts(新)

流程:
1. 檢查 sizeBytes
   - > 5MB(Claude API 單張上限)→ 回:「圖片太大了,可以截小一點再傳嗎?或直接告訴我地點名稱。」
   - LINE 上傳通常 < 1MB,5MB 邊界基本不會碰到
2. 送 Claude Sonnet (vision) 抽取
3. 抽到具體景點 → 後續流程同 Story A/B/C(Notion write、KV write、Flex card)
4. 沒抽到具體景點 → 回:「看起來不是景點相關的圖,可以再試一次,或直接告訴我地點名稱。」

D. Vision Extraction Prompt

src/capabilities/places/extract.ts:
- 加 extractFromImage(imageBase64, mimeType): Promise<ExtractedPlace>
- System prompt 改寫為支援圖片場景:
  "圖片可能是:IG 截圖 / FB 截圖 / LINE 對話截圖、實體店家招牌或環境照片、雜誌剪報、傳單、菜單、官網截圖。
   先判斷圖中是否有具體景點/店家資訊,有的話依下方 schema 抽取。
   若整張圖看不出明確景點(例如純風景照、人像、迷因),回 { error: 'no_place_detected' }。"
- 輸出 schema 跟現有 extraction 一致(spec §7.2)
- ai_inferred_fields 對 image extraction 通常會比較多,這是預期的
